# 0084 — Public-repo portability scrub: CI-gated path hygiene and a formalized qa-proof/ shape

Status: Accepted
Date: 2026-09-13

## Context

This repository is public. Its tracked files — agent prompts, skill bodies, ADRs, tests, and the evidence tree under `qa-proof/` — are readable by anyone, and some of that text was authored while working on one particular machine. A census of tracked content found four recurring classes of machine-local detail that do not belong in a public repository's tracked text: (A) an OS-account name embedded inside an absolute path's `Users` segment, (B) a local clone root written as an absolute path — either the native Windows drive-letter form, or the MSYS/Git-Bash single-letter mount-form spelling Git Bash substitutes for it — (C) other local, unrelated project names mentioned in passing, and (D) pointers into an out-of-repo personal knowledge store. Only A and B are mechanized by CHECK 25 below; D1 states why C and D are not. Two concrete instances anchor this ADR:

- `.claude/agents/qa-tester.md`'s "Artifact-path requirement" section states the two sanctioned proof-artifact directories as literal machine-local absolute paths, immediately above a Python code block that, as tracked today, computes only one of those two directories correctly and portably (via the `CLAUDE_PROJECT_DIR` environment variable, falling back to `git rev-parse --show-toplevel`) — the second directory is named only in prose, never derived in code. One of the literal bullets is redundant with — and less portable than — the code directly below it; the other names a directory the code doesn't compute at all. D4 below repairs both: the code is extended to derive the second directory, and both bullets are replaced with person-agnostic prose that the (now-complete) code block backs.
- The proof-posting mechanism qa-tester and `/ship` both rely on (committing a proof artifact and posting a PR comment that embeds it) was specified in [ADR-0049](0049-claude-preview-browser-driver.md) D3 as a convention — "commits the image to the PR branch at `qa-proof/<prd-num>/<slug>.png`" — without ever being given a machine-checkable definition of what path shapes under `qa-proof/` are actually sanctioned. Nine tracked files under `qa-proof/design/` and `qa-proof/forensics/` predate any such definition and do not match the `qa-proof/<prd-num>/**` numeric shape the convention's own prose implies.

A prior draft of this ADR reached a round-3 `adr-critic` strict-stop (rule #19/CRI-001) on six findings, all in the same class: missing YAML frontmatter (and its downstream consequences — no `rule_ids`, no `supersedes`, nothing for `tools/gen_rules.py` to render), a missing `## Propagation` section, and two dispositions (the CI self-collision risk below, and the nine non-conforming `qa-proof/` files) that were named but not resolved with a mechanism. This document is a full re-authoring, not an edit of that draft — the prior text is gone; every decision below was re-derived from the current repository state.

**Basis for re-entry, stated rather than assumed:** that prior draft's strict-stop was tracked as issue **#1325** (opened 2026-09-02; closed by the operator 2026-09-14, with the `needs-human` label cleared) — at the time this document was drafted, the strict-stop had not yet been adjudicated by the operator. CRI-001's strict-stop binds the revision loop of the artifact that hit it; it does not bar a full re-authoring from starting its own round counter, and neither drafting nor critiquing this document published anything or bypassed any gate — the round-3 discipline (CLAUDE.md rule #19, ADR-0048 D1) governs revision-in-place of a blocked draft, not the decision to discard it and start over. But that was a procedural point about this document's own round counter, not a resolution of #1325 on its own: this ADR's **landing was gated on the operator clearing the `needs-human` label on #1325**, independently of whatever verdict `prd-critic` and `adr-critic` returned on this text — and the operator has since done so (issue closed, label removed), clearing the way for this document to land. Landing this ADR before that adjudication would have silently resolved an open human-escalation item by fait accompli, which is exactly what the `needs-human` surface (CLAUDE.md I5) exists to prevent. See also §6/Open questions.

## Decisions

### D1 — Portability-scrub CI check (CHECK 25 / VER-011): tracked files must be scrubbed of machine-local absolute-path detail, except in named evidence directories

CI gains a new check, **CHECK 25 (PORTABILITY-SCRUB)**, appended in `tools/ci-checks.sh` immediately after the current last check (**CHECK 24b**, spanning `tools/ci-checks.sh:1123-1133` — CHECK 24 has two legs sharing one banner echo at `:1110`, then 24a DRAIN-LEDGER's own `if`/`fi` at `:1111-1121` and 24b the grill-me `/goal`-absence check's `GRILL_SKILL=` assignment at `:1123` followed by its own `if`/`fi` at `:1124-1133`; 24b is the one CHECK 25 follows) and before the `--- CI SUMMARY ---` block (the comment separator opening that section is at `:1135`, followed by the `# Summary` line at `:1136`; the actual `echo "--- CI SUMMARY ---"` runs at `:1139`). It greps **tree-wide over `git ls-files --cached`** — every tracked file, not a PR's diff — for **two** of the four hygiene classes named in Context — A and B; the reason C and D are out of mechanized scope is stated below, as a decision, not an omission.

**Subject set, stated by precedent rather than invented fresh:** `tools/ci-checks.sh` has no argument parsing at all — no `case` on `$1`, no `getopts`, no `while` on `$#`; its header comment reads `Usage: bash tools/ci-checks.sh` — so a `--full` mode does not exist anywhere in this script and this ADR does not authorize building one. The correct model is the in-repo precedent this ADR should have cited from the start: **CHECK 13 (secrets gate, ADR-0068 D2, `tools/ci-checks.sh:666-844`)**. Two of its own comments are stale in exactly this way: the section's introductory "Scope:" comment at `:675` ("tracked non-binary files in git diff HEAD...") and the comment at `:782` ("Get tracked files from git diff...") both claim a diff-scoped subject set, but the code that actually runs, at `:786-789`, is `subprocess.run(['git', 'ls-files', '--cached'], ...)` — tree-wide, not diff-scoped, at both sites. That comment/code mismatch is a defect in CHECK 13's own prose (`:675` and `:782` both), not a pattern to repeat here. CHECK 25 and CHECK 26 both evaluate `git ls-files --cached` output, exactly like CHECK 13, and this ADR states that plainly rather than inventing a diff-scoped or dual-mode subject set no other check in this file has. This is also what makes [ADR-0083](0083-honest-substrate.md) D3 / VER-009 ("a check's subject set is defined rather than assumed") satisfied rather than violated by CHECK 25 and CHECK 26.

**Why two new checks rather than two more patterns inside CHECK 13 (parsimony, argued rather than assumed):** CHECK 13 already owns a tree-wide grep-plus-allowlist shape, so folding Class A/B pattern matching into it — reusing its loop, its `tools/secrets-allowlist.txt`, its remediation message — is the cheaper-looking option, and this ADR rejects it explicitly rather than by omission. CHECK 13's rubric is credential/secret-shaped: its patterns match things that look like assignment-shaped key/token/secret values, GitHub PAT prefixes, AWS access-key IDs, hex-looking values, and a Shannon-entropy heuristic over scanned strings (`tools/ci-checks.sh:690-713`) — no PEM/private-key-header pattern and no connection-string pattern are among them — and its allowlist entries record "this looks like a secret but is reviewed as not one." A Class A/B hit is a different failure class entirely — a syntactically valid, non-secret path that merely names the wrong machine — and an entry in `tools/secrets-allowlist.txt` recording "this looks like a machine-local path but is reviewed as documentation" would silently widen what that file means to a future reader auditing it for actual credential exemptions. CHECK 26 (D2) is even further from CHECK 13's rubric: it validates a directory-naming convention, not a content pattern, and shares essentially nothing with the secrets gate except both being grep/path-based. This is the same parsimony principle CLAUDE.md's critic-parsimony meta-rule applies to critics — reuse only when the new concern is already inside the existing mechanism's rubric — applied here to CI checks instead: CHECK 13's *allowlist-file shape* is reused by analogy (D1's exclusion design above), but its *rubric and its actual file* are not, because portability hygiene is not secret hygiene.

- **Class A** — an OS-account-name segment inside a `Users` path component, matched in a **person-agnostic** way: a `Users` directory component followed by a path separator and an account-name-shaped segment, checked in both slash directions (the verbatim pattern, and its measured counts, are given below — the account-segment placeholder is never left unexpanded). The pattern must never hard-code any specific maintainer's account name — a guard that encodes the very name it exists to catch is self-defeating and silently stops working the day the account name changes.
- **Class B** — a local clone root written as an absolute path, in either of two on-disk spellings: the native Windows drive-letter form, or the MSYS/Git-Bash single-letter mount-form Git Bash substitutes for it. Both spellings name the same underlying hazard and CHECK 25 ships one pattern per spelling (two arms). Both are measured below, not asserted.
- **Class C** — mentions of other, unrelated local project names that have no reason to appear in this repository's own text. **Not mechanized** — see below.
- **Class D** — pointers to an out-of-repo personal knowledge store or personal-skill location. **Not mechanized** — see below.

**Why Class C and D have no pattern (a decision, not an omission):** Class A and B are expressible person-agnostically because the hazard is structural — a path *shape* (a `Users` segment, a drive letter, a mount-form root) that can be matched without ever naming the specific account or drive it happens to be on this machine. Class C and D have no such structural shape: catching "mentions of this other unrelated project's name" or "a pointer to that personal knowledge store" requires a pattern that literally contains the other project's name or the personal-store's path — the exact string the check exists to keep out of a public repository. Shipping that pattern would mean committing the private detail to tracked, public CI source in order to detect it, which defeats the purpose more directly than the risk it guards against. CHECK 25 is therefore scoped to Class A and B only; Class C and D stay census-only categories, addressed (if ever) by a differently-shaped mechanism this ADR does not attempt — see also the Alternatives section's rejection of a full sweep.

**Class A — measured, not asserted:** a bare word match, `[Uu]sers`, over-matches: measured directly against this repository at commit `c06df1758c118a156d5da8367532768369847215`, it hits **9 files, 24 occurrences** — most of them the ordinary English word ("Users find the new docs intuitive", `.claude/agents/prd-critic.md`'s own criterion-quality examples) with no path structure at all. The fix mirrors arm 1's discipline: require the `Users` token to be followed immediately by a path separator and an account-name-shaped segment, guarded by a word boundary so the match cannot start mid-word:

```
\<[Uu]sers[\\/][A-Za-z_][A-Za-z0-9_.-]{2,}
```

At the same commit this pattern matches **3 files, 14 occurrences** tree-wide, with exactly **one** occurrence outside `qa-proof/**` + `decisions/**`, at `tests/test_session_start_hookspath_1282.py:61` (a comment using the placeholder segment `name`, not a real account name). The other two files are both under `qa-proof/forensics/` and `qa-proof/design/` — grandfathered evidence (see Subject set below), not new leaks. Unlike Class B, Class A needs only one arm: the `Users` segment itself is spelled identically in the native Windows form and the MSYS/Git-Bash mount form (only the drive root before it differs, which Class B already covers separately), so a single pattern catches both on-disk spellings without a second arm.

**Class B, arm 1 — drive-letter form (measured, not asserted):** the obvious shape, a bare `[A-Za-z]:[\\/][A-Za-z_]`, over-matches badly. Measured directly against this repository at commit `c06df1758c118a156d5da8367532768369847215`: **43 files, 100 occurrences**. Most of those are not paths at all — a capitalized word immediately followed by a colon (`VERDICT:`, `stderr:`) is indistinguishable from a drive letter under that shape, because nothing stops the letter before the `:` from itself being the tail of a longer word. The fix is not a tighter separator class — narrowing to backslash-only trims the bare count from 43 files/100 occurrences to 38 files/90 occurrences, a real but small reduction that still leaves the dominant false-positive shape (a capitalized word ending in a colon, indistinguishable from a drive letter regardless of which separator follows it) largely intact; it is a **word-boundary guard on the drive letter itself**, so a real drive letter must stand alone rather than end a longer word. Guarding the boundary alone (`\<[A-Za-z]:[\\/][A-Za-z_]`) brings the count to **14 files, 44 occurrences** at the same commit. CHECK 25's actual pattern adds one more constraint on top — a path-shaped segment (2 or more characters, drawn from a class that allows the space/dot/hyphen a real directory name can contain, so a segment like "Program Files" still matches) followed by a second path separator, confirming genuine multi-level path structure rather than a single stray token:

```
\<[A-Za-z]:[\\/][A-Za-z_][A-Za-z0-9_ .-]{2,}[\\/]
```

At commit `c06df1758c118a156d5da8367532768369847215` this arm-1 pattern matches **13 files, 41 occurrences**. PRD §2 keeps its criteria behavior-only and does not repeat this count (see D1's note on that below); this ADR's own count is falsifiable against landing-day HEAD: if a fresh measurement of this exact pattern disagrees with 13/41 (mechanically expected, since new commits land between this ADR and the slice merging), the disagreement itself is not a defect. This is a decision record, not living documentation — the re-measurement this note calls for happens **once, during the landing slice's implementation, before this ADR file is committed to `decisions/`**; an ADR is never edited post-acceptance (glossary: "ADR"), so this sentence is not a standing licence to reopen this file later. If a future PR needs different counts, that is a new decision, recorded in a superseding ADR, not an edit here.

**Class B, arm 2 — MSYS/Git-Bash mount-form spelling (measured, not asserted):** Git Bash silently rewrites a native drive-letter root into a single-letter mount path (e.g. the drive-letter root becomes a single ASCII letter between two slashes at the start of a path), and arm 1's pattern does not match that spelling at all — it has no drive letter, no `:`, and no backslash for arm 1 to anchor on. This is a distinct on-disk spelling of the same Class B hazard (a path naming the local clone root), not a new class, and needs its own arm:

```
(^|[^A-Za-z0-9_])/[A-Za-z]/[A-Za-z_][A-Za-z0-9_.-]{2,}/
```

The leading `(^|[^A-Za-z0-9_])` is the ERE-expressible equivalent of a word-boundary guard on the single mount letter (GNU ERE has no lookbehind; this alternation — start-of-line, or a non-word character immediately before the leading `/` — does the same job without one), preventing the pattern from firing on a `/x/y/` substring embedded inside a longer non-path token. Controls checked: `.claude/skills/ship/SKILL.md` and `tools/ci-checks.sh` do **not** match (no false positive on their ordinary relative-path prose); a real mount-form path does match. Measured directly at commit `c06df1758c118a156d5da8367532768369847215`: **7 files, 12 occurrences** tree-wide. CHECK 25's Class B is the union of arm 1 and arm 2 — a tracked line fails the check if either arm matches it.

**Subject set (per the ADR-0083 D3 principle that a check's subject set must be defined, not assumed):** CHECK 25 evaluates every tracked file **except** three exclusions, excluded by construction:
- `qa-proof/**` — an evidence directory. [ADR-0083](0083-honest-substrate.md)'s own Propagation section already grandfathers `decisions/`, `qa-proof/`, `.claude/logs/`, and `.claude/worktrees/**` as evidence throughout; this ADR reaffirms that precedent for `qa-proof/` specifically rather than re-litigating it.
- `decisions/**` — the immutable ADR archive. ADRs are never edited (glossary: "ADR"); a hygiene check that could fail against `decisions/**` would create pressure to hand-edit a supposedly-immutable file, which this repository's whole supersession convention exists to prevent.
- `tools/portability-allowlist.txt` itself — this file is deliberately **path-anchored** (each entry names a specific file plus a literal substring of one of its lines), unlike CHECK 13's **content-anchored** `tools/secrets-allowlist.txt`, whose entries match by text alone wherever they appear and so happen to self-exempt that allowlist file as an accident of that design, not by intent. A path-anchored allowlist gets no such accident: `tools/portability-allowlist.txt`'s own seed entries are themselves literal substrings of the hazard lines they exempt (worked-example paths and the like), so without this third exclusion CHECK 25 would scan the allowlist file, match its own entries against its own Class A/B patterns, and fail on the very file that exists to prevent those failures elsewhere. Excluding it by construction — rather than content-anchoring it like CHECK 13's file (which would lose the per-line, per-path selectivity this D1 relies on below), or hashing/encoding its entries (which would defeat the auditability a plain-text allowlist exists to provide) — is the only option that keeps both properties CHECK 25 needs: real per-line selectivity, and a maintainable, human-reviewable file.

**Exclusion for hazard-documenting prose — an allowlist FILE, not a hard-coded list (dissolves the self-inflicted deadlock a closed list would create):** even the shipped patterns still match lines that are not leaks — comments whose whole purpose is to document the hazard CHECK 25 exists to catch, written with a generic placeholder or a worked example rather than committing a new real path. An earlier version of this D1 tried to close that gap with a hard-coded, ADR-only-growable exclusion list — but a list that only a superseding ADR can extend, combined with an implementer whose shipped Class A/B regex is even slightly wider than the one measured here, is a deadlock: the next legitimate hazard-documenting comment has nowhere to go except failing CI until an ADR lands to exempt it. CHECK 13 already solved this exact problem for the secrets gate: an **allowlist FILE**, `tools/secrets-allowlist.txt` (loaded at `tools/ci-checks.sh:734`, 1307 bytes today), reviewed like any other tracked file, with a remediation message (`:829`) telling a contributor exactly how to add an entry. CHECK 25 adopts the same shape: a new tracked file, **`tools/portability-allowlist.txt`**, is CHECK 25's exclusion mechanism instead of a list baked into this ADR's prose. (See Subject set above: the file itself is also excluded from CHECK 25's own scan, by construction, so it cannot trip the check it feeds.)

Two differences from CHECK 13's allowlist, both deliberate:
1. **Path-anchored, not path-agnostic.** CHECK 13's patterns match by content anywhere in any scanned file; a portability exemption is instead anchored to the specific file it exempts, because the same placeholder text (e.g. a generic worked-example path) legitimately appearing in one file's hazard-documentation comment must not blanket-exempt an unrelated file that happens to contain similar-looking text.
2. **Substring-anchored, not line-number-anchored** — this is also the fix for a hazard CLASS 8 of this review named: a path-plus-line-number exemption silently drifts the moment anything is inserted above it in that file, either un-exempting the hazard-documenting line (a spurious CI FAIL) or exempting a different line entirely (a real leak passing silently). Each entry instead pairs a path with a **literal substring of the exempted line**, so the exemption tracks the text, not its position — an insertion elsewhere in the file cannot shift it onto the wrong line. Every entry also carries a **required reason comment** (mirroring CHECK 13's `:829` remediation message), and a contributor with a genuine new hazard-documentation line adds an entry, with its reason, **in the PR that needs it** — no superseding ADR required, because extending this file is not amending an immutable decision record; it is maintaining a tracked allowlist, the same as `tools/secrets-allowlist.txt` today.

**Initial contents, seeded at landing:** the file ships with exactly the eight entries derived below — the union of every hit Class A, Class B arm 1, and Class B arm 2 each produce outside the `qa-proof/**`/`decisions/**` exclusions, at commit `c06df1758c118a156d5da8367532768369847215`. (An earlier derivation pass measured against Class B's arm 1 alone; that was wrong, because it silently assumed no other shipped class or arm could hit prose the arm-1 pass never measured — this list is the full union.) Two files seed the list with **two entries each**, which is exactly why substring- rather than file-anchoring matters: `tools/deploy-handshake.sh` is the clearest case — `:143` and `:144` are two halves of one comment, one spelling the drive-letter form and the other the mount form; a file-level exemption would have exempted both by accident rather than by measurement, and would keep exempting the whole file even after a real leak landed on line 145.

The eight seed lines (cited by path and line, at the commit measured, for evidentiary purposes only — the allowlist file itself anchors each by path + literal substring, not by these line numbers, once implemented; none of the eight lines is quoted here, the same discipline this ADR applies to every other citation):

- `bootstrap.sh:289` — a comment naming the MSYS drive-letter-to-mount-form path-conversion behavior the surrounding code guards against. (Class B arm 1.)
- `tests/test_promote_ack_880.py:46` — a comment illustrating that same MSYS conversion, using a generic placeholder path rather than a real one. (Class B arm 1 and arm 2, same line.)
- `tests/test_promote_gate_parse_1036.py:70` — a near-identical illustrative comment, in a second file. (Class B arm 1 and arm 2, same line.)
- `tests/test_promote_sentinel_order_1038.py:70` — the same illustrative comment again, in a third file. (Class B arm 1 and arm 2, same line.)
- `tests/test_session_start_hookspath_1282.py:61` — a comment documenting a bash tilde-expansion hazard, using a generic placeholder account name. (Class A and Class B arm 2, same line — a different line from the next entry, in the same file.)
- `tests/test_session_start_hookspath_1282.py:201` — a comment giving a worked example of the absolute `hooksPath` value the test exists to detect. (Class B arm 1.)
- `tools/deploy-handshake.sh:143` — a comment giving the same kind of worked example, for the absolute `hooksPath` a misconfigured hook may write. (Class B arm 1.)
- `tools/deploy-handshake.sh:144` — the same comment's second sentence, spelling the identical hazard in mount form. (Class B arm 2 — a different line from the entry above, in the same file.)

That is **8 seed entries across 6 files**. Unlike D2's qa-proof/ grandfather list (which stays a closed, ADR-only-growable list — a different kind of exception, see D2's parsimony note), `tools/portability-allowlist.txt` is a living, reviewer-gated file: it grows via ordinary PR review, the same discipline `tools/secrets-allowlist.txt` already operates under today.

**Not on this list, because it is not hazard-documenting prose:** `tests/test_hook_parsimony_877.py:241`, `:266`, and `:306` also match Class B arm 2, but each is a live `tool_input.file_path` value inside a synthetic hook payload, not a comment — a real occurrence of the hazard, not a description of it. These are fixed, not excluded; see D5.

**Also checked during the mandatory pre-commit re-measurement, and confirmed clean — no match, so no allowlist entry:** eight further candidate lines, raised during slice decomposition as possible additional Class A/B hits, were re-verified directly against the three patterns exactly as shipped above, in isolation, at landing time (commit `c06df1758c118a156d5da8367532768369847215`, using two independent tools — Python's `re` module and GNU `grep -E` — so neither a translation error nor a single-tool blind spot could hide a real hit): `tests/test_handshake_msys_1091.py:6,8,11,14`, `tools/deploy-handshake.sh:84,88`, `tests/test_session_start_hookspath_1282.py:8`, and `docs/decision-log/2026-08-21-operations-batch.md:12`. None match. The `/x/...`-shaped mentions (`test_handshake_msys_1091.py:6,8,11,14`; `deploy-handshake.sh:84,88`) either have no second path separator after the mount letter (`:6`, `:84`) or are followed by an ellipsis rather than a real path-shaped segment (`:8`, `:11`, `:14`, `:88`), so arm 2's `[A-Za-z_][A-Za-z0-9_.-]{2,}/` requirement is never satisfied. `test_session_start_hookspath_1282.py:8`'s doubled-backslash spelling breaks arm 1 immediately, since the character right after the first separator is a second backslash, not `[A-Za-z_]`. `docs/decision-log/2026-08-21-operations-batch.md:12` matches neither arm — there is no second path separator after the path-shaped segment, so arm 1's multi-level-structure requirement (above) is never satisfied; that line is also a Class C mention (an unrelated local project's name), which this ADR's Class C treatment above already places outside CHECK 25's mechanized scope by design — an existing, named gap this reconciliation pass confirms rather than creates. Re-running the full pattern union against `git ls-files --cached` (minus the three Subject-set exclusions) at the same commit reproduces this ADR's own accounting exactly — the eight seed entries above, plus D4's two and D5's three, for **13 hits, zero unaccounted** — confirming the seed list is complete rather than merely a floor that happened not to grow. No pattern was loosened, tightened, or converted to a file-level exemption to reach this result. This reconciliation is corroborated, not contradicted, by a `captured` issue raised independently during slice decomposition naming these same eight candidates: its own framing hedges one of the four files as a match "under a broad arm-2 reading" rather than the literal shipped pattern, and proposes no pattern change — consistent with a future, deliberately-deferred question about whether to broaden CHECK 25's classes, not a defect in the classes as shipped here. That capture is left open and untouched by this ADR; it is the correct home for that separate question, not a reason to alter D1's patterns, seed list, or exclusions now.

**Consequence, stated honestly rather than presented as free:** a check that must exempt the prose describing its own hazard is weaker than it looks, because the exemption is exactly where a real leak could hide — a new `tools/portability-allowlist.txt` entry, shaped like the seed eight but actually naming a new real path, would pass CHECK 25 silently. This ADR accepts that trade-off in exchange for not failing CHECK 25 on its own documentation. The trade-off is bounded by the allowlist's own shape, not by a closed count: each entry is anchored by path plus a literal substring — never a bare file-level exemption, never a line number that could drift — so a neighboring real leak elsewhere in the same file still fails the check. The control against a bad entry is ordinary reviewer scrutiny of the allowlist file itself on the PR that adds it, the same discipline `tools/secrets-allowlist.txt` already operates under today (D1) — not a superseding-ADR requirement, which D2's separate, genuinely closed grandfather list still uses for its own different reason (a fixed historical count, not a living exception surface).

**Disposition of finding 2 (the self-inflicted CI deadlock), stated as a decision with its consequence:** Because CHECK 25's subject set excludes `qa-proof/**` by construction, the sanctioned `qa-proof/<prd-num>/<slug>` proof-commit ([ADR-0049](0049-claude-preview-browser-driver.md) D3's mechanism) can never collide with it, structurally, not by convention. The consequence is that `qa-proof/` content itself remains entirely unscrubbed by CI going forward — a screenshot or evidence file committed there may still carry machine-local detail — and that is an accepted, named trade-off, not a silent gap; a future decision to scrub `qa-proof/` content is possible but is out of scope here and would need its own ADR. D2 below is this ADR's answer to that named gap, not an unrelated second decision riding along in the same document: since CHECK 25 cannot and structurally does not scrub `qa-proof/` content, CHECK 26 is what gives that directory any CI coverage at all going forward — a naming-shape check rather than a content check, but coverage nonetheless — so D1 and D2 are coupled by construction: D2 exists because D1's own exclusion would otherwise leave `qa-proof/` entirely unchecked by anything this ADR ships.

**Note on rule-id provenance (VER-011):** `VER-011` already appears once in this repository's tracked text, inside [ADR-0083](0083-honest-substrate.md)'s own Alternatives-considered prose, which discusses — and rejects — a finer three-way split of its D3/D5 statement that would have used `VER-011` for D4. ADR-0083's frontmatter claims only `VER-009` and `VER-010`; it never claims `VER-011`. That prose mention is not a reservation, and `VER-011` remains free for this ADR to mint — but a reader who greps `VER-011` before this ADR lands and finds only that sentence should not conclude ADR-0083 already claims it.

**Bootstrap-mode ([ADR-0004](0004-bypass-prevention.md) D2):** CHECK 25 binds forward from the merge of the slice that ships it — it evaluates the tracked tree as `git ls-files --cached` reports it at CI-run time, never git history, and no prior commit is rewritten or retroactively judged. This is not a grandfather clause covering leftover hits, because there are none to grandfather: D4 and D5 land in the same PR as CHECK 25 itself, and together with the seeded `tools/portability-allowlist.txt` (D1 above) they account for every Class A/B occurrence this ADR's own measurements found outside `qa-proof/**`/`decisions/**` at commit `c06df1758c118a156d5da8367532768369847215` (the third subject-set exclusion, `tools/portability-allowlist.txt` itself, is a new file created by this same landing PR, so it contributes no pre-existing occurrences to net against). So the tree is already clean under the new check at the moment it starts enforcing — bootstrap-mode here describes the check's temporal scope (forward from landing, not backward into history), not a backlog of pre-existing violations being waved through.

### D2 — qa-proof/ shape check (CHECK 26 / VER-012): the sanctioned shape is `qa-proof/<prd-num>/**`, nine pre-existing files are named and grandfathered

CI gains a second new check, **CHECK 26 (QA-PROOF-SHAPE)**, appended directly after CHECK 25. It walks the tracked files under `qa-proof/` and asserts that every path matches `qa-proof/<prd-num>/**`, where `<prd-num>` is a bare numeric segment (the shape [ADR-0049](0049-claude-preview-browser-driver.md) D3's own examples always used, e.g. `qa-proof/574/tab1-architecture.png`). This is the first time that shape has been given a machine-checkable definition; before this ADR it existed only as an unstated convention in prose.

**Disposition of finding 3 (qa-proof/ tracked-status), by name:** the following nine currently-tracked files do not match the numeric shape and are explicitly **grandfathered** — CHECK 26 must special-case exactly this list and no more:
- `qa-proof/design/judges-and-verdicts.md`
- `qa-proof/design/winner-architecture.md`
- `qa-proof/design/winner-staging.md`
- `qa-proof/forensics/code-health-auditor.md`
- `qa-proof/forensics/event-pipeline-autopsy.md`
- `qa-proof/forensics/github-trail-assessor.md`
- `qa-proof/forensics/process-retrospective.md`
- `qa-proof/forensics/purpose-archaeologist.md`
- `qa-proof/forensics/topology-ontologist.md`

This is bootstrap-mode (glossary: "bootstrap-mode"): the shape binds forward from this ADR's landing slice; no retroactive rename or move of the nine files is owed by this ADR. Any *new* file added under `qa-proof/` after landing must either match the numeric shape or be added to this exact list by a superseding ADR — CHECK 26 does not grow its grandfather list on its own authority.

**Parsimony:** CHECK 26 is a separate check from CHECK 25 rather than a third pattern folded into it, because the two check genuinely different things — CHECK 25 matches path-shaped *content* wherever it appears in tracked text; CHECK 26 validates a *file-naming convention* scoped to one directory tree and has no content pattern to match at all. They share only the mechanical shape of "walk tracked files, fail on a mismatch," which is also all CHECK 25 shares with CHECK 13 (D1's parsimony note above) — sharing that much scaffolding is not, by itself, a reason to merge two checks whose actual pass/fail rubrics have nothing in common.

### D3 — Partial supersession of ADR-0049 D3: the proof-posting mechanism is preserved verbatim; only its path scope is newly formalized

[ADR-0049](0049-claude-preview-browser-driver.md) D3 established the proof-posting mechanism still in force today (preserved through [ADR-0050](0050-headless-playwright-browser-driver.md) and [ADR-0074](0074-live-browser-qa-driver.md), per `decisions/README.md`'s own Status-column note on ADR-0049's row): the orchestrator commits the qa-tester-returned proof path under `qa-proof/<prd-num>/<slug>` and posts a PR comment embedding it via its raw GitHub URL, while qa-tester itself stays read-only. **Nothing about that mechanism changes here.** What changes is that D2 above gives its previously-informal path scope a precise, CI-checked definition for the first time. This ADR's `supersedes: ["ADR-0049 D3"]` frontmatter records that narrow, per-decision partial supersession; per the precedent [ADR-0083](0083-honest-substrate.md) set for its own partial supersession of [ADR-0057](0057-hook-fail-loud-contract.md) D2, this is recorded as a **Status-column annotation on ADR-0049's own row in `decisions/README.md`**, not by editing `decisions/0049-claude-preview-browser-driver.md`, `decisions/0050-headless-playwright-browser-driver.md`, or `decisions/0074-live-browser-qa-driver.md` — all three stay immutable, unedited by this ADR (see Propagation).

### D4 — Concrete repair: qa-tester.md's literal-path duplication

`.claude/agents/qa-tester.md:497-498`'s "Artifact-path requirement" section currently states the two sanctioned proof directories as literal machine-local absolute paths, directly above a Python block that, as tracked today, derives only **one** of those two directories portably — `PROOF_DIR` (`qa-proof/<prd-num>/`), computed from `CLAUDE_PROJECT_DIR`/`git rev-parse --show-toplevel`; the review-shots directory is never computed anywhere in that block, only named in the prose bullet this repair removes (`:497`) and in a relative mention elsewhere in the section (`:500`). Both literal bullets are **Class B, arm 1** instances (drive-letter-rooted absolute paths, per D1's classification — not Class A, and not the illustrative placeholder text D1's `tools/portability-allowlist.txt` seed entries describe). The repair has two parts, not one: the two literal bullets are replaced with person-agnostic descriptions — "the gitignored review-shots log directory" and "the repo-root-derived `qa-proof/<prd-num>/` directory" — **and** the Python block is extended to compute the review-shots directory from the same repo-root base already used for `PROOF_DIR`, so the code block (not the prose above it) becomes the section's sole source of both actual paths. Doing only the first half — deleting the two literal bullets without extending the code — would leave the review-shots directory's absolute path derived nowhere in the file, which is worse than the original duplication, not better.

This repair also dispositions [ADR-0061](0061-rule-20-mechanization.md) D5, the decision this section's own heading cites ("Artifact-path requirement — ROOT-absolute only (ADR-0061 D5)"): D5 requires production-verify artifact paths to be root-absolute, not worktree-relative (`decisions/0061-rule-20-mechanization.md:31`). The repair preserves that requirement rather than weakening it — both directories stay root-absolute after the fix, they are simply *derived* (via `CLAUDE_PROJECT_DIR`/`git rev-parse --show-toplevel`) rather than *machine-literal*. D5 separately describes these as "gitignored proof directories," while `qa-proof/` is in fact tracked; that mismatch predates this ADR, is not introduced or resolved by this repair, and is left alone here rather than papered over. This is one of the two concrete files this ADR repairs directly (the other is D5 below); it is also, going forward, exactly the kind of hit CHECK 25 (D1) now catches mechanically.

### D5 — Concrete repair: test_hook_parsimony_877.py's hard-coded clone-root test payloads

`tests/test_hook_parsimony_877.py:241`, `:266`, and `:306` each hard-code the local clone root, in Class B arm 2's mount-form spelling, as the `tool_input.file_path` value of a synthetic hook payload — live test data, not documentation, and a real occurrence of the Class B hazard D1's exclusion list does not (and should not) cover. Left as-is, CHECK 25 would fail on its own first run against this repository's tracked tree, contradicting D1's disposition-of-finding-2 principle that a check may only fail a subject on an invariant it actually owes ([ADR-0083](0083-honest-substrate.md) D3): a test payload owes no invariant that requires it to name this specific machine's clone root.

The fix is behavior-preserving: each payload's `tool_input.file_path` value has its clone-root prefix replaced with a neutral placeholder root, keeping the suffix the hook under test actually matches on. That placeholder root's shape is constrained, not arbitrary: it must be a **multi-letter** root segment (e.g. `PROJECT_ROOT` or a multi-character mock directory name), never a bare single ASCII letter standing alone between two path separators — a single-letter root would itself match Class B arm 2's pattern (D1: `(^|[^A-Za-z0-9_])/[A-Za-z]/[A-Za-z_][A-Za-z0-9_.-]{2,}/`) and reintroduce, in the very payload meant to remove it, the exact hazard CHECK 25 lands in the same PR to catch — failing the check on its own first run against this repository. The three payloads are checked by three different downstream assertions, not one repeated pattern, and no single characterization covers all three accurately:

- `:241`'s payload (suffix `.claude/agents/reviewer.md`) is checked by two `assertIn` calls, at `:249` and `:254` — the first for the basename `reviewer.md`, the second for the fixed marker string `AS-AUDIT`, both inside the resulting `subagent-edits.log` text. These two are genuine filename/marker-substring checks, and the basename is unaffected by whatever the root prefix is.
- `:266`'s payload (suffix `.claude/agents/implementer.md`) is checked by `assertEqual([], events)` at `:274` — an absence assertion: it asserts `workflow-events.jsonl` stayed empty for this hook path, not that any string is present anywhere. It never inspects the path's content, so it is satisfied identically regardless of the root.
- `:306`'s payload (suffix `tools/ci-checks.sh`, deliberately outside `.claude/agents/**`) is checked by `assertEqual("", log_text)` at `:314` — also an absence assertion, this time for `subagent-edits.log` staying empty, because the path falls outside the nudge hook's matched prefix in the first place, not because of anything the assertion reads out of the path.

So the fix is behaviorally identical in all three cases, but for two different reasons, not one: `:241`'s pair of assertions look at the basename/marker, which the root-prefix swap leaves untouched; `:266` and `:306`'s assertions are absence checks that never look at path content at all, so they are indifferent to the root by construction rather than by only matching a substring of it. This is the second of the two concrete files this ADR repairs directly (the first is D4).

## Consequences

- CI gains two new, deterministic checks (CHECK 25, CHECK 26); a PR introducing a new machine-local absolute path (Class A, or Class B in either its drive-letter or mount-form spelling) outside `qa-proof/**`, `decisions/**`, and `tools/portability-allowlist.txt` itself, or a new non-conforming file under `qa-proof/` that isn't on the D2 grandfather list, now fails CI instead of merging silently.
- `.claude/generated/_global.md` is itself a tracked, regenerated file, so it becomes a new CHECK 25 subject the moment this ADR lands, exactly like every other tracked file — D1 gives it no special treatment. If a future ADR's hand-authored `_RULE_STATEMENTS` entry in `tools/gen_rules.py` ever embedded a Class A/B path, CHECK 25 would fail on the regenerated output; because `.claude/generated/_global.md` is DOC-001 generated (never hand-edited, never allowlisted around), the fix belongs at that rule-statement source, not in `tools/portability-allowlist.txt`. Named here honestly as a new, currently-unguarded surface, not a gap this ADR silently leaves undocumented.
- CHECK 25 is scoped to Class A and B only; Class C and D are explicitly not mechanized, because a pattern for either would have to contain the very private string it exists to keep out of a public repository (D1) — this is a decision, not a gap this ADR overlooked.
- `qa-tester.md`'s artifact-path section is portable — no reader needs to know, or infer, any one maintainer's machine layout to understand where proofs are written. `test_hook_parsimony_877.py`'s three synthetic payloads no longer hard-code the clone root either (D5) — both concrete repairs land in the same PR as the two new checks, so CHECK 25 does not fail on its own first run.
- `qa-proof/` content itself (screenshots, evidence markdown) remains unscrubbed by CI — an explicitly accepted trade-off (D1), not an oversight.
- CHECK 25's Class A/B patterns are also weakened by a necessary exclusion for prose that documents their own hazard (D1): a new tracked file, `tools/portability-allowlist.txt`, seeded at landing with eight entries derived per class against every arm the check ships, each anchored by path plus a literal substring — never a line number, never a whole file. The allowlist file itself is excluded from CHECK 25's subject set by construction (D1), so it cannot trip the check it feeds. This is an accepted, bounded weakening, not a silent one: a new entry shaped like the seed eight but naming a real path would also pass silently, and the control against that is ordinary reviewer scrutiny of the allowlist file on the PR that adds an entry — the same discipline `tools/secrets-allowlist.txt` (CHECK 13) already operates under — not a superseding-ADR requirement, which stays reserved for D2's separate, genuinely closed grandfather list.
- The nine pre-existing non-conforming `qa-proof/` files are named once, here, and never need re-justifying — CHECK 26 treats them as a closed, fixed list.
- `tools/gen_rules.py`'s `RULE_IDS_BASELINE` conservation constant and its companion assertion in `tests/test_loc_cap_1162.py` both move from 92 to 94 in the same PR that lands this ADR (two new rule_ids: VER-011, VER-012) — see Propagation.
- `decisions/README.md` gains ADR-0084's own index row and an annotation on ADR-0049's existing row at landing time; neither edit is performed by this draft (see Propagation — both are owed-at-landing, following the same convention already visible on ADR-0049's, ADR-0050's, and ADR-0055's rows in that file today).

## Alternatives considered

- **Scrub `qa-proof/` content too, rather than excluding it.** Rejected: `qa-proof/` is evidence, and [ADR-0083](0083-honest-substrate.md)'s Propagation section already established the precedent that evidence directories are grandfathered rather than edited after the fact — scrubbing forensic evidence after it was written would falsify the historical record those files exist to preserve. If ever wanted, that is a separate, deliberate decision, not a side effect of this one.
- **Mint a new rule-id scope (e.g. `hygiene` or `portability`) instead of reusing `scope: "verification"`.** Rejected on the same grounds [ADR-0083](0083-honest-substrate.md)'s own Alternatives section used: `tools/gen_rules.py` parses exactly one `scope` per ADR, and both new checks are direct applications of [ADR-0083](0083-honest-substrate.md) D3's "a check's subject set must be defined, not assumed" principle to the qa-tester/proof-artifact verification subsystem — the existing `verification` scope is the correct home, not a new one.
- **Perform a full repo-wide Class A–D sweep in this same ADR/PRD.** Rejected under rule #1 (YAGNI) and rule #2 (walking-skeleton mindset): the concrete repairs in D4 and D5 plus the two new CI checks are the walking skeleton; a broader sweep is a legitimate follow-up but does not block this decision, and rule #16 leaves its slicing (if pursued) to the slicer, not to this ADR.
- **Leave the MSYS/Git-Bash mount-form spelling uncaught, and narrow the Goal to say so.** This was the cheaper route and was rejected: it would leave three live occurrences of the exact hazard this PRD's premise is about removing (`tests/test_hook_parsimony_877.py:241/266/306`) sitting in tracked text, uncaught by CI, while the Goal's own prose claimed no new machine-local path could land unchecked. Adding the mount-form arm (D1) and neutralizing those three payloads (D5) costs one more regex arm and three literal-value edits — small next to the walking skeleton already being built — and keeps the Goal's absolute phrasing honest rather than requiring it to carry a caveat.
- **Rewrite git history to purge existing hits.** Rejected: destructive, out of scope, and no existing rule requires it; bootstrap-mode (glossary) grandfathers prior state rather than demanding retroactive cleanup.

## Open questions

- Whether `qa-proof/`'s binary growth over time (accumulating screenshots) eventually needs a retention policy, pruning, or Git LFS is explicitly out of scope and left open.
- The exact wording of the three owed-at-landing `decisions/README.md` edits (ADR-0084's new row; the annotation on ADR-0049's row; removal of the placeholder "Note on ADR-0084") is left to whoever performs the landing, following the existing annotation style already visible on that file's other superseded/narrowed rows — this ADR does not pre-write that text (see Propagation).
